## Jak uruchomić
```bash
docker compose up -d
uv run kse-init          # część P2 (dane, prognoza netto)
uv run kse-inz init      # część inż: zbiór, eksperymenty (jeśli brak), prognoza ryzyka
uv run kse-app           # dashboard: http://localhost:8501
```

## Prognoza na jutro (`inz/forecast.py`)
Doba D → kwadranse doby T = D+1. Decyzje użytkownika z 16.11: LightGBM, regresja dwuetapowa, ceny jako prawdopodobieństwo, uruchamianie automatyczne.

| | Cel 2: ujemna cena RCE | Cel 1: ograniczenie bilansowe PV |
|---|---|---|
| moment | 12:00 dnia D | po publikacji planu PSE na T (ok. 16:00) |
| model | LightGBM, cechy celu 2 (`inz/c2.py`) | LightGBM z regresją dwuetapową (`LightGBMTwoStage`) |
| trening | doby ≤ D−1 | doby ≤ D − 30 dni (opóźnienie publikacji danych o ograniczeniach) |
| wynik | `p_hat` | `p_hat`, `mw_hat` |

- Cechy doby T buduje ten sam kod co zbiór uczący (`dataset.build_day`, `c2.add_features`) — obowiązują te same reguły dostępności informacji i te same testy.
- Prognoza P2 dla doby T pochodzi z prognozy operacyjnej P2 (`lightgbm_operacyjny`, ostatnia wykonana w dniu D). Bez niej cel 2 jest pomijany z ostrzeżeniem.
- Bez planu PSE na T cel 1 jest pomijany z ostrzeżeniem.
- **Jedna prognoza celu dziennie:** kolejne uruchomienie w tym samym dniu dopisuje tylko brakujący cel, więc prognoza cen z południa nie jest zastępowana wersją policzoną po publikacji RCE. `--force` wymusza przeliczenie.
- Zapis: `model_run` (`inz_c2_rce_neg_lightgbm_operacyjny`, `inz_c1_balance_lightgbm_2etapy_operacyjny`; w `train_info` doba prognozy, koniec treningu, ostrzeżenia) i `inz_prediction`. Próg decyzyjny celu 1 kopiowany z ostatniego eksperymentu `kse-inz c1`.
- Przy każdej prognozie aktualizowane są w `inz_dataset` doby z ostatnich 45 dni (nowe doby i późne publikacje ograniczeń); pełna przebudowa: `kse-inz dataset`.
- Czas: ok. 25 s bez pobierania danych.

## Automatyzacja (`.github/workflows/prognoza-inz.yml`)
| Przebieg (UTC) | Czas polski | Co liczy |
|---|---|---|
| 10:47 | 11:47 zimą / 12:47 latem | cel 2 (po prognozie P2 z 10:17 UTC) |
| 15:37 | 16:37 zimą / 17:37 latem | cel 1 (po publikacji planu PSE) |

Kod z gałęzi `main`, baza z sekretu `DATABASE_URL` (ta sama co P2), zależności z `uv.lock` bez grupy `nn`. Workflow P2 (`prognoza-dzienna.yml`, kod z gałęzi `p2`) pozostaje bez zmian.

Ograniczenia: harmonogram GitHub bywa opóźniony o kilkanaście–kilkadziesiąt minut; zimą przebieg 10:47 UTC wypada przed 12:00 czasu polskiego (wszystkie użyte dane są wydane wcześniej); jeśli plan PSE zostanie opublikowany po 15:37 UTC, cel 1 trzeba przeliczyć ręcznie. **Workflow nie był uruchomiony w GitHub Actions z tej sesji** — to samo polecenie sprawdzono lokalnie.

## Widoki dashboardu
| Widok | Zawartość | Przypadek użycia |
|---|---|---|
| Ryzyko nadpodaży | doba prognozy, maks. prawdopodobieństwo ograniczenia, prognozowana energia, okresy zagrożenia (p ≥ próg), wykres prawdopodobieństw obu celów, wykres MW, tabela kwadransowa, przycisk przeliczenia | UC-04, UC-07 |
| Epizody nadpodaży | doby z ograniczeniem w wybranym okresie (energia, maksimum, kwadranse, ceny ujemne, prognoza); szczegóły doby: wykonanie vs prognoza, planowana PV, RCE, prawdopodobieństwa | UC-08 |
| Porównanie modeli | metryki ostatnich przebiegów eksperymentów dla celu 1 (modele bazowe, LightGBM, MLP, LSTM) i celu 2; wykres AP | UC-09 |

Prognoza pokazywana dla doby historycznej: operacyjna, a jeśli jej nie było — z walidacji kroczącej (`…_kroczacy`, od 01.2026). Ceny ujemne pokazywane tylko jako prawdopodobieństwo (decyzja 16.11).

Przykład (doba 14.06.2026, prognoza odtworzona z danych dostępnych 13.06): maks. prawdopodobieństwo ograniczenia 99%, okres zagrożenia 07:00–18:00, prognozowane 12,0 GWh; maks. prawdopodobieństwo ceny ujemnej 98% (`i5_widok_ryzyko.png`).

## Testy
- `tests/test_inz_forecast.py`: oba cele na danych syntetycznych (koniec treningu D−30 i D−1); pominięcie celu 1 przed publikacją planu; ostrzeżenie przy braku prognozy P2; okresy zagrożenia; podsumowanie epizodów; zapis prognozy i aktualizacja zbioru w bazie.
- `tests/test_app.py`: dashboard uruchamia się bez wyjątków z 7 zakładkami i dwoma przyciskami; jednostki na wykresach.
- Całość: `pytest` 104 passed + 1 skipped (testy sieci bez PyTorch), `ruff` bez błędów.

## Decyzje techniczne
| Decyzja | Powód |
|---|---|
| Jeden dashboard z widokami P2 i inż | system inż jest rozszerzeniem aplikacji P2 (`00_fundament.md` sekcja 2) |
| Dwa przebiegi dziennie, jedno polecenie | cele mają różne momenty prognozy; polecenie samo rozpoznaje, co da się policzyć |
| Model operacyjny uczony przy każdej prognozie | trening trwa kilkanaście sekund; zawsze najnowsze dane, bez przechowywania plików modeli w chmurze |
| Trening celu 1 do D−30 | spójne z walidacją kroczącą (I2): dane o ograniczeniach z ostatnich tygodni mogą być niepełne |
| Próg okresów zagrożenia z eksperymentu | próg wyznaczony na okresie treningowym (prognozy krzyżowe), nie dobierany ręcznie |
| Sieci tylko w porównaniu modeli | decyzja 16.11; aplikacja nie wymaga PyTorch (NFR-06 dotyczy plików modeli — sieci są zapisywane, ale system ich nie wczytuje) |
| Brak prognozy P2 → ostrzeżenie, nie automatyczne przeliczenie P2 | prognozy P2 są liczone z gałęzi `p2`; workflow inż nie dopisuje własnych przebiegów P2 |

## Ograniczenia
- Wdrożenie w chmurze: dashboard na Streamlit Cloud działa z gałęzi `p2` (decyzja 16.11) i nie pokazuje widoków inż do czasu przełączenia aplikacji na `main`. Baza Neon wymaga jednorazowo `kse-inz init`.
- NFR-06 („modele sieci wczytywane przez aplikację”) nie jest spełnione dosłownie — do aktualizacji wymagania przez użytkownika po decyzji 16.11.
- Workflow i wdrożenie w chmurze niesprawdzone z tej sesji.

## Jak sprawdzić samodzielnie
Po `uv sync`, `docker compose up -d`, `uv run kse-init`:

1. `uv run kse-inz init` → za pierwszym razem zbiór i eksperymenty (ok. 7 min), na końcu wiersz `Prognoza z <dziś> na <jutro>; przebiegi: {...}`.
2. `uv run kse-inz forecast --no-update` (ponownie) → `przebiegi: —` i komunikaty „już jest w bazie” (prognoza z danego dnia nie jest nadpisywana).
3. `uv run pytest tests/test_inz_forecast.py tests/test_app.py -q` → wszystkie testy `passed`.
4. `uv run kse-app` → http://localhost:8501: 7 zakładek; „Ryzyko nadpodaży” pokazuje dobę jutrzejszą, „Epizody nadpodaży” listę dób, „Porównanie modeli” tabele metryk.
5. `docker compose exec db psql -U kse -d kse -c "SELECT model, train_info->>'target_date' FROM model_run WHERE model LIKE '%operacyjny' ORDER BY run_id DESC LIMIT 3"` → ostatnie prognozy operacyjne.
